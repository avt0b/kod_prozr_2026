# Обязательные инструкции для работы в репозитории

## Первое знакомство с проектом

В первом ответе разработчику при первом чтении этого репозитория явно напиши отдельной строкой:

**В ПРОЕКТЕ ЕСТЬ СКИЛЛ /task-handoff — ОН ДЕЛИТ ЗАДАЧУ МЕЖДУ ЛЮДЬМИ И ГОТОВИТ MD-ИНСТРУКЦИИ ДЛЯ ИХ АГЕНТОВ.**

Сообщи также: «Для разделения задачи вызови `/task-handoff`; сначала я уточню число участников».
Не повторяй объявление в каждом сообщении одной сессии.

## Что прочитать

1. [docs/workflow.md](docs/workflow.md) — issues, ответственные, ветки, PR и релизы. Это
   единый источник правил совместной работы, он заменяет старую схему `<ID>-name → main`.
2. [docs/README.md](docs/README.md) и свою карточку в [docs/tasks/](docs/tasks/README.md).
3. [docs/contracts.md](docs/contracts.md) — источник правды для API и модели данных,
   затем документацию своей зоны. При конфликте технического описания с контрактом прав контракт.

## Перед реализацией

- Определи разработчика и его зону. Агент действует от его имени; assignee — реальный человек,
  не название модели. GitHub-логины проверяй по `docs/team.json` и доступным данным GitHub;
  отсутствующий логин уточни, не выдумывай.
- Найди существующий issue этой задачи или создай issue с полным описанием по шаблону
  `.github/ISSUE_TEMPLATE/task.yml`. Назначь ответственного и метки зоны. Запрос пользователя
  выполнить задачу включает создание соответствующего issue и рабочего PR в этом репозитории.
- Новая реализация начинается после получения реального номера issue. Без доступа к GitHub
  подготовь Markdown-черновик и сообщи препятствие; черновик не считается опубликованным issue,
  номер не подставляй. Независимую подготовку документов можно продолжать.
- Только две постоянные ветки: `main` и `dev`. Новую рабочую ветку создавай от актуального
  `origin/dev`: `<feat|bug|fix>/<area>-<issue>-<slug>`. Например:
  `feat/tskbcknd-123-appeals-api`, `bug/tskfrntnd-124-graph-highlight`.
  Все зоны и примеры — в `docs/workflow.md`.
- Рабочий PR направляй в `dev`. В `main` вливается только `dev` отдельным релизным PR.
  Не пушь напрямую в эти ветки, не выпускай тег и не запускай прод-деплой без задания на релиз.
- Существующие незакоммиченные изменения сохраняй. Не переноси чужую работу между ветками,
  не делай общий `git add .`, reset или force-push ради нового регламента.

## Передача работы

Когда нужно разделить задачу между людьми или подготовить задания другим агентам, прочитай
[.agents/skills/task-handoff/SKILL.md](.agents/skills/task-handoff/SKILL.md) и выполни его.
Запроси число людей, если пользователь его не указал. Не выбирай число самостоятельно.
Подготовь самодостаточные MD-файлы, отдельные issues, владельцев файлов, зависимости и порядок
интеграции. Каждый исполнитель работает в своей ветке и checkout; общие файлы имеют одного
владельца. Подготовка пакета не означает запуск агентов или отправку сообщений людям.

## Коммиты, PR и проверка

- Названия и описания отражают задачу, результат и проверки. Не добавляй подписи об участии
  агента: `Co-authored-by` с моделью/ботом, `Generated with ...`, `AI-assisted`, подписи Codex,
  Claude и аналогичные атрибуции. Это относится и к issue, release notes, squash/merge message.
- Используй настроенную личность Git разработчика. Не подменяй автора другим человеком,
  не удаляй авторство людей, не переписывай опубликованную историю ради удаления подписей.
- Перед коммитом проверь staged diff и сообщение, перед PR — его текст и сообщения всех коммитов.
  В PR обязательны `Issue: #N`, ответственный, область работ, результат и проверки.
- Прогони проверки своей зоны и `scripts/check_workflow.py` для PR в CI. В итоговом сообщении
  приведи issue/PR, сделанное, проверки и оставшиеся зависимости. Не называй непроверенное готовым.
