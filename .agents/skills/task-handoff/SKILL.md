# Task handoff

Подготовь пакет заданий, который разработчик может отправить другим людям без истории чата.
Этот навык планирует передачу работы; сам не запускает исполнителей и не делает релиз.

## Контекст и число участников

Прочитай корневой `AGENTS.md`, `docs/workflow.md`, `docs/team.json`, карточки участников
и техническую документацию затронутых модулей. Если текущий checkout относится к другому
проекту, сначала установи целевой репозиторий; не переноси его правила и логины автоматически.

Если пользователь не указал число людей, **сначала спроси**:
«На скольких людей делим задачу? Учитывать тебя как исполнителя?»
Не выбирай число вместо пользователя и не выпускай финальные задания до ответа. Пока ждёшь,
можно прочитать код и зависимости. Если число дано явно, повторно его не спрашивай.
Неоднозначное «три человека плюс я» трактуй как четыре исполнителя, если автор тоже пишет код;
если участие автора неясно, уточни это до распределения.

Установи состав участников и координатора. Используй подтверждённые имена/логины из реестра;
недостающие назначения уточни. Не назначай человека исключительно по свободному месту в списке.
Если независимых частей меньше, чем участников, объясни зависимости и выдели отдельную
ответственность за тесты/интеграцию или документацию; не создавай фиктивную параллельность.

## Декомпозиция и договорённости

1. Найди или создай родительский issue с общим результатом, критериями приёмки, метками зон,
   `coordination` и координатором. Создай отдельные исполнимые issues на каждого участника,
   ссылающиеся на родителя; каждый имеет одного основного assignee. Подготовка issue входит
   в передачу задачи по этому навыку. Проверяй реальные assignees, labels и номера на GitHub.
2. Зафиксируй исходный SHA `origin/dev`, состояние контракта и внешние зависимости.
   Для всех участников явно запиши `dev` как базу и ветки по реальным номерам своих issues.
3. Разбей задачу по результатам и владению файлами. Для каждого пути/набора файлов укажи
   единственного владельца на этап. Широкие пересекающиеся области вроде `backend/**` и
   `backend/src/modules/appeals/**` не являются раздельным владением.
4. Особенно явно назначь владельцев `contracts.md`, типов API, wiring, роутеров,
   `pyproject.toml`, lockfiles, CI, compose, миграций и документации общей доски.
   Другие исполнители описывают требуемую правку в отчёте, а не редактируют этот файл сами.
5. Сначала согласуй и выдели интерфейсы/контракт. Для зависимой работы запиши блокирующий PR
   и условие начала после его merge в `dev`. Не предлагай всем независимо менять общий
   интерфейс, создавать миграцию с одной ревизией или пересобирать один lockfile.
6. Составь граф зависимостей без циклов и порядок PR. Если один файл нужен на двух этапах,
   укажи передачу владения только после приёмки/merge первого этапа. При изменении границ
   обнови все затронутые задания, а не только файл координатора.

Для независимых рабочих мест нужны отдельные checkout/worktree и ветки. Для этого пакета
нельзя запускать агентов в общем изменяемом checkout. Если назначение или внешний доступ
недоступны, явно укажи блокер и подготовь черновик; не придумывай номер issue, assignee или SHA.

## Пакет Markdown

Создай `docs/handoffs/issue-<parent-number>/README.md` и по одному `<NN>-<owner>.md`.
Если родительский issue ещё не опубликован, используй `docs/handoffs/draft-<slug>/`
и пометь весь пакет «ЧЕРНОВИК — НЕ НАЧИНАТЬ РЕАЛИЗАЦИЮ» до публикации и назначения issues.

Шаблон исполнителя и структура файла координатора:
[references/handoff-template.md](references/handoff-template.md). Прочитай его при генерации.

Каждый файл исполнителя должен быть самодостаточным: адрес репозитория, человеческий владелец,
issue/родитель, ветка, исходный SHA, цель, разрешённые и запрещённые файлы, зафиксированные
интерфейсы, зависимости, критерии приёмки, команды проверок, base PR и формат отчёта.
Вставь точное объявление `/task-handoff` из `AGENTS.md` для первого знакомства получателя.
Повтори ключевые ограничения веток и сообщений коммитов, чтобы пересланный MD задавал
правильный старт даже без предыдущего чата. Большие технические документы можно ссылать,
но критичные договорённости и границы должны быть изложены в самом задании.

README координатора содержит состав команды, карту владения, зависимости/этапы, порядок
интеграции, общую проверку и правило закрытия родительского issue. Сам координатор тоже
получает отдельный файл, если входит в число исполнителей.

## Проверка перед выдачей

- Число заданий совпадает с согласованным числом людей; у каждого есть реальный результат.
- У каждого issue один основной владелец, нужные метки и ссылка на родителя; все номера проверены.
- На каждом этапе пути записи не пересекаются; общие файлы перечислены явно, включая новые.
- Зависимости ацикличны; нет начала реализации до обязательного контрактного PR.
- SHA существует, ветки имеют ожидаемую базу `dev`, каждый рабочий PR направляется в `dev`.
- Получатель понимает задачу из одного файла, может запустить проверки и знает формат отчёта.
- Нет секретов, персональных токенов и служебных подписей в публикуемых заданиях/issue.

В ответе дай ссылки на все MD и issues, назови порядок запуска и конкретные блокеры.
Не отправляй файлы людям автоматически. Только отдельный прямой запрос пользователя
разрешает рассылку, запуск исполнителей или интеграцию; число участников само такого запроса
не означает. Слияние и релиз остаются отдельными действиями по `docs/workflow.md`.
