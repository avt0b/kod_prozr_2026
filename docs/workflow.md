# Совместная работа: issues, ветки и передача задач

Регламент действует для всей команды и всех инструментов разработки. Обязательный вход для
агентов — [AGENTS.md](../AGENTS.md), задача по людям — [tasks/](tasks/README.md), технический
контракт — [contracts.md](contracts.md). Старое правило `<ID>-name → main` заменено этим документом.

## 1. Ответственные и метки

исполнителем. Одной метки `back` недостаточно: нужен assignee с реальным GitHub-логином.

Машиночитаемый реестр — [team.json](team.json). Задача документации может быть назначена
любому участнику. Если GitHub не позволяет назначить указанного человека, сообщи об этом:
не подменяй его другим assignee и не выдавай запись имени в тексте за назначение.
Приглашения и права доступа меняет владелец репозитория отдельно.

Метки хранятся в [.github/labels.json](../.github/labels.json):

| Метка | Область |
| --- | --- |
| `back` | бэкенд, БД, API |
| `front` | фронтенд |
| `devops` | инфраструктура и CI/CD |
| `ai` | LLM, ML, анализ и оценка |
| `data` | данные и генератор |
| `docs` | документация и регламент |
| `coordination` | родительская задача с несколькими исполнителями |
| `release` | выпуск из `dev` в `main` |

В issue обязательна хотя бы одна метка области; для межзоновой задачи указываются все нужные.
`coordination` и `release` дополняют метку области. Создать недостающие метки и `dev` из `main`:

```bash
python scripts/bootstrap_github.py --repo avt0b/kod_prozr_2026
```

Команда использует авторизацию `gh`, сохраняет существующие метки и ветки.

## 2. Issue до реализации

Перед новой задачей агент находит подходящий открытый issue или создаёт его по
[шаблону](../.github/ISSUE_TEMPLATE/task.yml). Дублировать существующий issue не нужно.
Карточки `B-02`, `F-11`, `OPS-03` и т. п. остаются ID плана, **это не номера GitHub issues**.

В issue обязательно описать:

- проблему, цель и наблюдаемый результат;
- ID плана, если он есть; исходные документы и текущую ситуацию;
- что входит в задачу и что остаётся за её пределами;
- ответственного, метки области и предполагаемого ревьюера;
- конкретные критерии приёмки и проверки;
- зависимости и ограничения по файлам; для подзадачи — родительский issue.

Номер в ветке берётся из **реально созданного issue**. Если доступа к GitHub нет, агент
пишет Markdown-черновик и сообщает, что публикация заблокирована. Придумывать номер,
писать «issue создан» или начинать новую реализацию без опубликованного issue нельзя.
Подготовку документов и изучение проекта продолжать можно.

Пример (сначала сохранить полное описание в файл, логин заменить реальным владельцем):

```bash
gh issue create --repo avt0b/kod_prozr_2026 \
  --title 'B-13: Анализ обращений' --body-file /tmp/appeals-task.md \
  --label back --assignee 1nsanexeEZ
```

После создания проверь через `gh issue view`, что assignee и метки действительно применились.

## 3. Постоянные и рабочие ветки

Постоянных веток две:

- **`main`** — проверенный код релизов. Из него выпускаются прод-релизы.
- **`dev`** — интеграция задач. Все новые рабочие ветки создаются от актуального `origin/dev`.

Рабочие ветки временные, одна ветка и один PR на самостоятельный issue:

```text
<type>/<area>-<github-issue-number>-<short-kebab-case-name>
```

| Часть | Значения |
| --- | --- |
| `type` | `feat` — новая возможность; `bug` — исправление ошибки; `fix` — обслуживание, документация, конфигурация, рефакторинг |
| `area` | `tskbcknd` (back), `tskfrntnd` (front), `tskdvps` (devops), `tskai` (ai), `tskdata` (data), `tskdocs` (docs) |
| номер | положительный номер issue именно этого репозитория |
| имя | короткое описание латиницей, в нижнем регистре, слова через `-` |

Примеры с условными номерами:

```text
feat/tskbcknd-123-appeals-api
bug/tskfrntnd-124-graph-highlight
fix/tskdvps-125-ci-cache
feat/tskai-126-person-matching
feat/tskdata-127-synthetic-generator
fix/tskdocs-128-api-contract
```

Создание при чистом рабочем дереве:

```bash
git fetch origin
git switch -c feat/tskbcknd-123-appeals-api origin/dev
```

Если уже есть незакоммиченная работа, сохрани её на месте и используй отдельный checkout/worktree.
Не переноси чужие изменения в новую задачу. Старые рабочие ветки переходят на этот процесс
отдельно: свяжи их с issues, перенеси только нужные изменения в ветки от `dev`. Опубликованную
историю не переписывай и несвязанную работу не переименовывай автоматически.

## 4. PR и приёмка в dev

Рабочий PR: `рабочая ветка → dev`, всегда со своего issue. При создании укажи `--base dev`,
поскольку ветка по умолчанию на GitHub может остаться `main`.

```bash
gh pr create --base dev --title 'B-13: Анализ обращений (#123)' --body-file /tmp/appeals-pr.md
```

В описании по [шаблону](../.github/pull_request_template.md) обязательна отдельная строка
`Issue: #123`. Номер должен совпадать с веткой. Укажи результат, границы, выполненные проверки,
зависимости и ответственного. Ревью — от другого участника своей зоны; изменение API/модели
проверяет и потребитель (бэк/фронт/ИИ). Контракт меняется в том же PR.

Перед merge:

1. Ветка содержит только изменения своего issue и не нарушает выделенные владельцам файлы.
2. CI зелёный, обязательные замечания ревью устранены, конфликтов с актуальным `dev` нет.
3. Проверены сообщение squash/merge, описания PR и сообщения коммитов.
4. После merge обновляются issue и карточка плана. Для обычной задачи это `done`, issue закрывается
   после проверки в `dev`. GitHub не всегда закрывает issue по `Closes` при merge в непервичную
   ветку, поэтому используй `Refs #N` и явно проверь закрытие после интеграции.

Родительский issue закрывает координатор после приёмки всех частей. Изменения процесса
проверяет Роман; готовность к релизу — Кирилл. Не делай merge только потому, что агент закончил.

## 5. Релиз dev → main

Релиз — отдельный issue с `release` и `devops`, ответственным и списком включённых задач.
Релизный PR имеет источник **`dev`**, базу **`main`** и строку `Issue: #N` релизного issue.
Создавать постоянные `release/*`, сливать рабочую ветку прямо в `main` или обходить `dev` нельзя.

Кирилл после зелёного CI и smoke-прогона принимает релизный PR. Для `dev → main` используем
merge commit, чтобы сохранялась общая история веток; после релиза синхронизируем `main → dev`
обычным merge, без reset/force-push. Релизный issue закрывается после синхронизации и проверки выпуска. Это служебный PR синхронизации с тем же release issue,
источник `main`, база `dev`; он не содержит новых задач и тоже проходит CI.

После слияния выпускается тег `vMAJOR.MINOR.PATCH` на проверенном коммите `main`.
**Целевой конвейер**: релизный тег → проверка, что коммит входит в `main` → сборка/проверки →
деплой по ключу из GitHub Secrets → health/smoke. Рабочие ветки и `dev` прод не деплоят.
Тег `demo-v1` из плана — снимок демо; он не заменяет production-тег `v*`.
Настройку конвейера и секретов делает Кирилл отдельной задачей; этот регламент сам его не включает.
Ключи в репозиторий, issues и handoff-файлы не помещать.

Защита веток на GitHub — отдельная настройка владельца/DevOps: для `main` и `dev` требуются PR,
ревью и успешные проверки `backend`, `frontend` (workflow `CI`) и `policy` (workflow `Workflow policy`); прямой push, force-push и удаление
должны быть запрещены. До включения защиты CI сообщает нарушение, но сам по себе не запрещает
администратору нажать merge. Новые проверки необходимо сделать required после их первого запуска.

## 6. Сообщения коммитов и PR

Сообщение описывает изменение, а не инструменты его подготовки. Например:
`fix(appeals): не привязывать однофамильцев (#123)`.

Не добавлять подписи об участии моделей/агентов ни в commit message, ни в PR/issue/release notes:
`Co-authored-by` с Claude/Codex/ботом, `Generated with ...`, `AI-assisted` и аналогичные подписи.
Ветки и названия PR тоже не содержат рекламных суффиксов инструментов.
Используется настроенная личность Git разработчика. Человеческое соавторство сохраняется;
не следует выдавать чужую работу за свою или менять автора на выдуманного человека.

Проверка перед публикацией:

```bash
git diff --cached
git log origin/dev..HEAD --format=full
```

CI проверяет атрибуции в новых сообщениях коммитов PR и в названии/описании PR, в том числе
сообщения, используемые для squash. Исторические коммиты не переписываем. Документация самого
навыка и технические названия продуктов не являются подписью об их участии в разработке.

## 7. Несколько исполнителей: /task-handoff

Инструкция навыка: [SKILL.md](../.agents/skills/task-handoff/SKILL.md).
При первом знакомстве агент объявляет его **БОЛЬШИМИ БУКВАМИ** по `AGENTS.md`.
Если клиент не распознаёт slash-команду, передай ему путь к этому файлу и запрос на выполнение;
для клиентов с обозначением `$skill` используется `$task-handoff`. Для Claude Code есть
[файл команды](../.claude/commands/task-handoff.md).

Координатор сначала спрашивает, на сколько людей делить задачу, если число ещё не указано.
Количество означает общее число исполнителей, включая координатора, если он пишет код.
Затем создаёт родительский issue и отдельный issue на каждого исполнителя. Все подзадачи
наследуют общий результат, но имеют разные ветки, владельцев файлов и критерии приёмки.

Пакет хранится в `docs/handoffs/issue-<parent>/`: `README.md` с картой интеграции и по одному
самодостаточному `<NN>-<owner>.md`. Эти MD можно отправить людям без истории чата.
Каждый содержит репозиторий, исходный commit, issue, ветку, assignee, файлы, контракты,
зависимости, проверки и формат отчёта. Если есть недоступный исполнитель, issue назначения
остаётся явно заблокированным; формальная готовность пакета не подменяет проверку назначения.

Один файл имеет одного владельца на этап, в том числе lockfile, миграции, роутеры, wiring,
CI и `contracts.md`. Согласованные интерфейсы вливаются первыми. Зависимая часть создаёт ветку
от `dev` после этих изменений; до того можно изучать задачу и готовить тестовые сценарии,
но нельзя молча копировать чужой незавершённый код. Если требуется передать файл другому,
координатор обновляет карту владения после merge первой части и уведомляет исполнителей
через обновлённые handoff-файлы. Разные ветки при одном изменяемом checkout изоляции не дают.

Координатор интегрирует PR по зависимостям и проверяет общий сценарий. Сам навык только
готовит пакет: не запускает субагентов, не отправляет сообщения людям и не делает релиз.
