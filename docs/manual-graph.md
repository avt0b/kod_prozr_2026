# Ручные аналитические схемы

Issue: #64. Ответственный: Егор. Зависимость: авторизация из PR #63.

В профиле служащего нажмите «Дополнить граф», создайте схему, добавьте
объект и на вкладке «Связи» выберите два объекта. Можно соединять ручные
объекты между собой и с узлами исходного графа этого служащего. У объекта
и связи есть название, пояснение и источник. Схемы сохраняются в PostgreSQL,
открываются после обновления страницы по параметру `?scheme=<UUID>`.

Ручные объекты подписаны «Внесено аналитиком» и имеют пунктирную рамку;
ручные связи отмечены карандашом. Пояснение и источник доступны в редакторе,
у объекта — также в инспекторе. Эти сведения не проверены автоматически,
не меняют исходные записи, балл риска, доказательства флагов и докладную.
При выборе флага ручные связи остаются фоновыми даже между узлами его цепочки.

На вкладке «Доступ» выберите активных пользователей и сохраните список.
Получатели могут только просматривать схему. Ссылка не выдаёт прав сама:
для открытия нужен выданный доступ. Удалите получателя из списка и сохраните,
чтобы отозвать доступ. Сервер запрещает последующие запросы сразу; открытый
клиент обновляется каждые 15 секунд и при возвращении в окно. Отзыв доступа
не удаляет уже просмотренные или скопированные сведения с чужого устройства.

## API

Префикс `/api/v1/graph-workspaces`, все запросы требуют Bearer JWT.

| Метод и путь | Действие |
| --- | --- |
| `GET /?official_id=<UUID>` | Свои и полученные схемы, до 100 последних |
| `GET /users?query=<строка>` | Поиск активных получателей, до 30; только ID и логин |
| `POST /` | Создать: `{official_id, title}`; владелец из сессии |
| `GET /{id}` | Объекты, связи, `can_edit`; `shared_with` только владельцу |
| `DELETE /{id}` | Удалить свою схему вместе с содержимым и доступами |
| `POST /{id}/nodes` | Добавить: `{kind, label, notes?, source?}` |
| `DELETE /{id}/nodes/{node_id}` | Удалить ручной объект и его ручные связи |
| `POST /{id}/edges` | Добавить: `{source_id, target_id, label, notes?, source?}` |
| `DELETE /{id}/edges/{edge_id}` | Удалить ручную связь |
| `PUT /{id}/shares` | Заменить список получателей: `{user_ids: UUID[]}` |

`kind`: person/company/organ/contract/appeal. Лимиты схемы: 50 объектов,
100 связей, 30 получателей. Название схемы — 120 символов, объекта — 200,
связи — 160, пояснение — 2000, источник — 500. Пустые названия после удаления
пробелов запрещены. Самосвязи и ссылки на объекты чужой схемы или отсутствующие
узлы исходного графа запрещены. Чтение и запись используют блокировку схемы
для согласованного снимка объектов, связей и прав.

401 — нет сессии; 404 — схема отсутствует или не выдан доступ; 403 — получатель
пытается изменить схему; 409 — лимит; 422 — неправильные данные/получатель.
Права проверяются сервером для каждого запроса; localStorage не используется.

Миграция `0005` создаёт отдельную схему `manual_graph` после `0004`.
Откат `alembic downgrade 0004` удаляет ручные схемы вместе с содержимым:
перед откатом сохраните нужные сведения. Исходные данные и авторизация остаются.

## Проверка

API-тесты покрывают сохранение, изоляцию схем, запрет записи получателю,
отзыв доступа, каскадное удаление связей, неизменность графа и флагов,
конкурентное чтение во время записи. Unit-тест проверяет наложение без
мутации исходного графа и исключение ручных связей из доказательств.
Playwright проверяет создание объекта и связи, reload, Escape, отсутствие
горизонтального переполнения на 1440/390 px в обеих темах; общий доступ
через интерфейс, вход второй учёткой, просмотр и отзыв доступа.

Локальная проверка 20.11.2026: lint/format, TypeScript, build, Ruff,
Mypy и 6 контрактов импортов прошли; frontend unit — 23/23, Playwright —
11/11 (редактор и существующий холст). Backend — 199/200; все 3 новых
API-теста прошли. Прежний `test_full_volume_seed_and_graph` нарушает порог
300 мс: 470 мс с изменениями и 472 мс на исходном коммите `995ad81`
в отдельном checkout на той же нативной PostgreSQL 18. Порог не ослаблялся.
Цикл миграции `0005 → 0004 → 0005` проверен на отдельной тестовой БД.
