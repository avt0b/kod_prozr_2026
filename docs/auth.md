# Авторизация и рабочий интерфейс

Issue: #62. Ответственный: Егор (`durnoi-chel`). Ревьюер: `avt0b`.

## Контракт

Все бизнес-эндпоинты `/api/v1` требуют `Authorization: Bearer <access_token>`.
Исключения: login, refresh, logout; `/health` остаётся публичным. Неверный или
просроченный токен возвращает 401 в существующем формате ProblemDetails.

| Метод | Путь | Вход | Ответ |
| --- | --- | --- | --- |
| POST | `/api/v1/auth/login` | JSON `{username, password}` | `{access_token, token_type: "bearer", expires_in, session_id, user: {id, username}}` и refresh cookie |
| POST | `/api/v1/auth/refresh` | HttpOnly cookie + разрешённый Origin | Такой же ответ, refresh заменяется |
| POST | `/api/v1/auth/logout` | Cookie, разрешённый Origin; при наличии access — Bearer | 204, отзыв сессии, удаление cookie |
| GET | `/api/v1/auth/me` | Bearer | `{id, username}` |

Логин нормализуется в нижний регистр; допустимы латинские буквы, цифры, `_ . -`,
до 64 символов. Для неизвестного пользователя и неверного пароля одинаковый ответ.
Вход ограничен десятью попытками в минуту на адрес клиента в одном процессе.
Для нескольких workers/реплик общее ограничение задаётся на ingress.

JWT подписан HS256 с проверкой алгоритма, issuer, audience, exp/iat/nbf, sub/sid
и назначения access. Срок по умолчанию — 15 минут. Каждый запрос также проверяет
активность пользователя и серверной сессии, поэтому выход отзывает уже выданный
access. Пароли — Argon2id с солью. Refresh — случайный непрозрачный токен; в БД
сохраняется только SHA-256. Cookie включает UUID сессии, стабильное случайное
доказательство для выхода и ротируемый секрет обновления. Для доказательства выхода
тоже хранится только SHA-256. Refresh ротируется под блокировкой строки; предыдущий
после обмена не принимается. Сессия имеет фиксированный срок 7 дней.

Cookie `kodprozr_refresh`: HttpOnly, SameSite=Strict, Path=/api/v1/auth, Secure
по умолчанию. Refresh и logout проверяют точный Origin по CORS_ORIGINS. Без
Origin они не выполняются. Frontend отправляет cookie с credentials=include.
Токены не пишутся в localStorage/sessionStorage. При reload сессия восстанавливается
через refresh; параллельные 401 внутри вкладки объединяются в один запрос.
Сессии разных вкладок могут потребовать повторного входа при одновременной ротации.
Выход использует стабильное доказательство и отзывает сессию даже при параллельной
ротации. Запросы и ответы клиента привязаны к userId/sessionId: запрос старой
сессии не повторяется от имени новой и не заполняет её кеш запоздалым ответом.

Права пользователей зависят от роли — см. раздел [Роли](#роли) (#70). Сброс пароля по почте
в этот этап не входит; новый пароль задаёт администратор.

## Установка

Для текущей тестовой версии есть публичные учётки `demo` (аналитик), `demo-citizen`
(гражданин) и `demo-admin` (администратор) с паролем `Demo-2026-Access!`.
Создать её на стенде: `uv run python -m src.core.infrastructure.create_demo_user`.
Кнопки быстрого входа по ролям подставляют эти данные, затем пользователь нажимает «Войти».
Данные намеренно включены в Git по запросу пользователя. Команда отказывается
создавать демо-пользователя при `APP_ENV=prod`; существующий чужой логин не заменяет.

Панель графа сохраняет положение при выборе флага: селектор раскладки остаётся
на месте и показывает «По цепочке», а место индикатора подсветки зарезервировано.
Проверка координат прошла на 1440/390 px в светлой и тёмной темах (4 теста).

1. Обновить зависимости: `cd backend`, `uv sync --locked`.
2. Задать `AUTH_SECRET` из генератора случайных значений (не менее 32 символов).
   Например, выполнить `python -c "import secrets; print(secrets.token_urlsafe(48))"`
   и сохранить результат в закрытом окружении сервера. Примеры не содержат рабочего ключа.
3. Выполнить `uv run alembic upgrade head`: миграция 0004 добавляет core.users
   и core.auth_sessions, не меняя существующие бизнес-таблицы.
4. Создать пользователя: `uv run python -m src.core.infrastructure.create_user egor`.
   Пароль вводится скрыто дважды, от 12 до 256 символов. Для автоматизации
   есть `--password-env ИМЯ_ПЕРЕМЕННОЙ`: значение не передаётся аргументом CLI.
5. Запустить backend и frontend обычным способом. В production: HTTPS,
   `APP_ENV=prod`, `AUTH_COOKIE_SECURE=true`, явные CORS_ORIGINS. Неверная
   production-конфигурация отклоняется при старте. Без ключа в dev вход даёт 503.

Frontend по умолчанию использует `/api/v1`; Vite проксирует `/api` на 127.0.0.1:8000.
Это позволяет одинаково работать на localhost и 127.0.0.1. При своём VITE_API_URL
нужно сохранить совместимость cookie по site: не смешивать эти два имени хоста.
В Docker-стенде nginx фронта (`frontend/nginx.conf`) проксирует `/api/` на `backend:8000`,
фронт собирается с `VITE_API_URL=/api/v1`. `make env` заполняет пустой `AUTH_SECRET`
случайным значением, `make seed`/`make reset` создают учётку `demo`
(отдельно — `make demo-user`), `make smoke` входит ею. Моки бизнес-ответов не обходят вход:
для авторизации нужен backend.

Параметры: AUTH_ACCESS_SECONDS (30–3600), AUTH_REFRESH_DAYS (1–30), AUTH_SECRET,
AUTH_COOKIE_SECURE. Только локальный HTTP использует `AUTH_COOKIE_SECURE=false`.
Истёкшие/отозванные записи auth_sessions можно удалять при обслуживании БД;
планировщик очистки этим PR не добавлен. Перед выдачей нового пароля текущему
пользователю администратор должен отозвать его сессии.

## Роли

Issue #70. Три роли (`core.users.role`, миграция 0006; существующие пользователи — аналитики):

| Роль | Что может | Стартовая страница |
| --- | --- | --- |
| Гражданин (`citizen`) | Регистрируется сам, подаёт обращения, видит свои обращения и их статус | `/citizen` |
| Аналитик (`analyst`) | Рабочее место: рейтинг, профили, граф, обращения и их рассмотрение (передать по подведомственности, закрыть), ассистент | `/` |
| Администратор (`admin`) | Всё, что аналитик, плюс раздел «Пользователи»: создание, смена роли, блокировка, новый пароль, удаление | `/` |

- Гражданин не видит анализ обращения, кандидатов и привязанных служащих: только текст,
  дату и статус («Принято», «На рассмотрении», «Передано по подведомственности», «Рассмотрено»).
  Связь с автором — `core.citizen_appeals`.
- Аналитиков и администраторов создаёт администратор (или CLI
  `create_user <логин> --role admin|analyst|citizen`); саморегистрация даёт только гражданина,
  роль из тела запроса игнорируется.
- Смена роли, блокировка и новый пароль отзывают все сессии пользователя.
- Последнего активного администратора нельзя разжаловать, заблокировать или удалить.
- Удаление пользователя с данными (например, владельца схем графа #64) возвращает 409:
  такого пользователя блокируют.
- Журнал аудита пока пишет `actor = analyst` для всех действий, персональный аудит — отдельная задача.

Демо-учётки тестового стенда (пароль `Demo-2026-Access!`, `make demo-user`):
`demo` — аналитик, `demo-citizen` — гражданин, `demo-admin` — администратор.
На странице входа — кнопки быстрого входа по ролям. Первый администратор на VPS:
`docker compose run --rm backend python -m src.core.infrastructure.create_user <логин> --role admin`.

## Совместимость

Фронтенд перенаправляет на `/login`, после успешного входа возвращает локальный
маршрут и query. На выходе очищает query-кеш. Ключи кейсов имеют прежнюю схему
значения v1, но разделяются UUID пользователя: `kod-prozr:workbench:v1:<userId>`.
Старый общий ключ сохраняется на устройстве, автоматически другим пользователям
не импортируется. Сохранение и сравнение продолжают работать после reload.

Скрипт smoke принимает `SMOKE_ACCESS_TOKEN` либо SMOKE_USERNAME/SMOKE_PASSWORD.
Браузерные тесты принимают E2E_USERNAME/E2E_PASSWORD. В текущем локальном стенде
одноразовые данные находятся в игнорируемом `.codex-build/local-auth.json`;
они не включены в репозиторий и память. CI создаёт отдельного тестового аналитика.

## Изменения интерфейса по наблюдениям

| Проблема до правок | Изменение | Проверка |
| --- | --- | --- |
| Презентация и повтор анимаций конкурируют с рабочими действиями | Презентация удалена; повтор анимаций позже убран совсем (#68) | Playwright: вход/выход, отсутствие презентации |
| На 390 px бренд профиля перекрывает возврат | Шапка в обычном потоке, инструменты сгруппированы рядом с навигацией | Снимки и границы header/back на 1440/390 |
| Общие действия профиля разбросаны по углам | Поиск, кейсы, сравнение и аккаунт в общей шапке; в графе только его управление | Визуальное сравнение, сценарии открытия панелей |
| Фильтры имеют четыре фиксированные разные ширины | Адаптивная grid-сетка, орган и минимальный балл стоят рядом на телефоне | Снимки рейтинга, проверки фильтра и отсутствия переполнения |
| Горизонтальный граф уменьшается в узкую полосу на телефоне | Две колонки начальной раскладки, ограниченная высота 440 px; выбранная цепочка сохраняет прежнюю логику | Графовые unit/Playwright, снимки светлой/тёмной темы |

Основа — реальные снимки до правок из `.codex-build/auth-layout-before`,
после — `.codex-build/auth-layout-after`. Шрифты и палитра не заменялись.
Управление рисками, контракты графа и набор связей не менялись.

Реализация опирается на [рекомендации FastAPI по JWT и Argon2](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/)
и [проверку обязательных claims в PyJWT](https://pyjwt.readthedocs.io/en/stable/api.html).

он безусловно ожидал сумму из моков и открывал отсутствующий в реальной БД UUID.
Теперь проверяет актуальную группировку и использует существующий профиль.

Ограничения: крупные графы по-прежнему требуют масштаба/панорамирования;
роли и восстановление доступа не входят в этап. Production deploy и merge
не выполнялись; перед production нужен отдельный review настройки HTTPS,
ключа, общих ограничений попыток и политики доступа организации.
