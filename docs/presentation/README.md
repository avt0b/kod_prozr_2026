# Презентация F-17

`kod-prozrachnosti-review.pptx` — 8 редактируемых слайдов 16:9. Текст, таблица метрик и заголовки
редактируются в PowerPoint; скриншоты встроены. Заметки докладчика содержат сценарий, оговорки и
источники из документации проекта.

Файл собирается скриптом `build.mjs` на публичной библиотеке [pptxgenjs](https://www.npmjs.com/package/pptxgenjs)
(версия закреплена в `package.json` и `package-lock.json`). Правки текста вносите в `build.mjs`, а не только
в `.pptx`: при следующей сборке ручные правки файла пропадут.

## Сборка

Нужен Node.js ≥ 22.18. Из корня репозитория:

```bash
npm ci --prefix docs/presentation      # pptxgenjs и playwright; node_modules в git не попадают
node docs/presentation/build.mjs       # → docs/presentation/kod-prozrachnosti-review.pptx
```

Входы сборки:

| Что                                                                                          | Откуда                                                                    | Слайд          |
| -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- | -------------- |
| Метрики качества                                                                             | `eval/report.json` (`make seed && make eval`), читаются при каждой сборке | 7              |
| Скриншоты и фрагменты                                                                        | `screenshots/*.png` (`screenshots.mjs`)                                   | 1, 3, 5, 6     |
| Факты прогона: место и балл Соколова до и после обращения, категория и движок разбора, флаги | `screenshots/stand.json` (`screenshots.mjs`)                              | 3, 5 и заметки |

Переменные: `REPORT` — другой путь к отчёту метрик, `OUT` — другой путь к результату. Без
`eval/report.json` или без нужных скриншотов сборка падает с понятной ошибкой: слайд 7 с выдуманными
числами не собираем.

**Слайд 7.** Левая колонка — риск-правила (`rules`: precision/recall R01–R06, ложноположительные кейсы,
R08, precision@10/@20). Правая — таблица разбора обращений, по столбцу на движок. Сейчас в отчёте только
фоллбэк на правилах (`appeals.fallback`). Если в отчёте появится LLM-прогон (`make eval EVAL_ARGS="--llm --limit 30"`
пишет `appeals["llm:<модель>"]`; поддержаны также `appeals.llm` и блок `llm` верхнего уровня с той же
структурой), рядом появится столбец LLM, а в подписи — размер выборки и доля ответов самой LLM.

## Скриншоты со стенда

`screenshots.mjs` проходит сценарий [demo.md](../demo.md) в Playwright (1920×1080): главная → новое
обращение H1 через форму → рейтинг → профиль Соколова → граф с цепочкой R01 → докладная. Нужен фронт,
подключённый к реальному API с сидами (не моки). Скрипт создаёт обращение, поэтому снимать нужно на
свежей БД.

### Пересъёмка одной командой

`reshoot.sh` делает всё подряд: свежая БД → скриншоты → сборка pptx. Запуск из корня репозитория;
перед ним нужен один раз `npm run browsers --prefix docs/presentation` (chromium для Playwright).

```bash
# стенд docker compose: make reset (тома сносятся, миграции и сиды), фронт http://localhost:3000
docs/presentation/reshoot.sh

# свой локальный стенд: БД из DATABASE_URL пересоздаётся, затем alembic upgrade head и сиды через uv
DATABASE_URL=postgresql+asyncpg://kodprozr:kodprozr@localhost:55437/kodprozr \
BASE_URL=http://127.0.0.1:5185 LLM_BASE_URL= docs/presentation/reshoot.sh
```

Во втором варианте бэкенд и фронт уже запущены и смотрят в эту БД. Пересоздаётся только БД на
`localhost`. Режим LLM при разборе нового обращения задаёт запущенный бэкенд, а при загрузке сидов —
`LLM_*` из окружения и `backend/.env`. После изменения сидов или анализа обращений (например, предрасчёта
AI-06) достаточно повторить ту же команду: цифры и подписи слайдов 3 и 5 берутся из нового `stand.json`.
Метрики слайда 7 команда не пересчитывает: если менялся анализ, сначала обновите `eval/report.json`
(`make eval`).

### Как устроен скрипт

`screenshots.mjs` перезаписывает `screenshots/`: полные кадры `overview`, `appeal`, `ranking`, `profile`,
`graph`, `report` и фрагменты для слайдов, обрезанные по элементам страницы (`ranking-top`, `profile-head`,
`appeal-main`, `graph-card`, `report-page`), а также `stand.json`. Кадры сначала снимаются во временную
папку и копируются в `screenshots/` только после успешного прохода всего сценария. Если какой-то шаг
падает, скрипт пишет название шага, адрес страницы и путь к `failure.png`, а `screenshots/` не трогает.

Перед съёмкой скрипт проверяет, что фронт работает не на моках и что Соколов ещё не на 1-м месте.
Если обращение уже отправляли, скрипт останавливается: снимать на таком стенде можно только явно,
через `ALLOW_STALE=1`. Другие переменные: `OUT_DIR` — снять в другую папку, `BROWSER_CHANNEL` — использовать
установленный Chrome, `STEP_TIMEOUT_MS` (по умолчанию 30 с) и `ANALYSIS_TIMEOUT_MS` (200 с: с LLM бэкенд
ждёт модель до 2 × 90 с) — таймауты ожидания элементов и разбора.

### Текущие скриншоты

Сняты 15.11.2026 командой `reshoot.sh` на отдельном локальном стенде: FastAPI + PostgreSQL с сидами
`data/generated`, фронт в dev-режиме, LLM не подключена, веса риска ADR-16. Соколов: 3-е место (73) →
1-е (88) после обращения, это совпадает с [demo.md](../demo.md). Разбор сделан фоллбэком на правилах
(`engine: fallback`), категория — `procurement` («Закупки»). По [demo.md](../demo.md) так и должно быть
без LLM: категорию `conflict_of_interest` ожидаем только с LLM, и это не проверено. Спикер называет
категорию, которая на экране; в заметках к слайду 5 это указано.
